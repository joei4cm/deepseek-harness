# Agent Note: 按书写语言的密度为文本计价

Status: implemented

[English](2026-11-23-script-aware-token-density.md) | 中文

## 问题

`dsh-token-meter` 把每个字符都按四分之一 token 计价。这个数值对英文散文足够接近，但提供方对 CJK 文本大约每字符计一个 token，因此中文会话的计价只有实际费用的四分之一左右。上下文指示器与自动压缩触发器读取同一个估算值，于是两者都低报：一个下一次请求实际携带一百二十万 token 的会话显示 24% 占用，压缩也从未提前到足以让请求留在窗口内。超窗的会话无法自救，因为压缩请求本身要携带它正试图缩短的历史。

必须有一个估算器同时服务 meter、压缩触发器、上下文构成、spill 策略与工具结果裁剪器，让它们的数字一致。

## 决策

估算器按每个字符所属语言的密度计价：ASCII 每字符 0.25 token，CJK 表意文字、假名与谚文 0.65，CJK 标点与全角形式 1.0，其他非 ASCII 0.4。ASCII 保持此前每 token 四字符，因此每个既有消费方都保留原有数值。

这些密度是实测得到的，不是挑选的。以 DeepSeek-V3 的字节级 BPE 分词器与本机由 llama.cpp 分词的 Qwen3.5 模型，对照英文散文、源码、JSON 与本仓库自己的中文文档，两个分词器的结果相差在 5% 以内。在已录制的 harness 会话与仓库内容上，平均绝对误差相对 DeepSeek-V3 从 18.5% 降到 10.9%，相对 Qwen3.5 从 21.6% 降到 14.1%。

## 曾考虑的替代方案

**按提供方使用精确分词器。** 已否决：本包已记录按提供方分词器的方案尚未决定，而每个提供方一个分词器会让同一份表面对不同消费方给出不同数字，而共享估算器正是为了保证这种一致。

**从提供方报告的用量中学习密度。** 已否决：提供方报告的是它所应答的那次请求的规模，而压缩请求应答的是整段历史的摘要，因此这个规模不是估算器所计价的那份表面的规模。两者之比不是密度，会扭曲之后每一次估算。

**把 ASCII 拆成字母、数字、标点与空白。** 已实测，未采纳：JSON 标点每个字符约计一个 token，英文散文每个字符约计五分之一，所以 ASCII 的费率其实是两个费率。拆开之后，相对 DeepSeek-V3 的平均误差只减少 0.4 个百分点（10.9% 降到 10.5%），相对 Qwen3.5 减少 0.8 个百分点（14.1% 降到 13.3%），而已录制会话上的最大少计从 26% 减半到 13%。但它会改变每一个 ASCII 数值，从而改变每个会话的 spill 预算、压缩阈值与工具结果裁剪上限。这笔取舍应当放在它自己的改动里，让被移动的阈值可以一并审阅。

## 后果

在本仓库的中文文档上，CJK 文本的计价与提供方的计数相差在 4% 以内，而不是低报 47%，因此压缩触发器与上下文指示器在提供方认为该触发的时点触发。

ASCII 数值不变。英文散文仍比提供方高约 22%，JSON 与工具输出仍低约 20%，因此 ASCII 会话的散文压缩比提供方要求得更早，密集工具输出的压缩比提供方要求的更晚。

liveshare 查看器 fixture 现在直接导入共享估算器而不是自行镜像，因此 fixture 的上下文构成不会与 meter 漂移。

## 测试

`packages/llm/token-meter/tests/estimate.spec.ts` 固定了每个语言类别、每一个 CJK 区间、每一个全角区间，并拿一段中文与 DeepSeek-V3 分词器公布的 token 数对照。
